# Intended deviations and strict choices (L1)

<!-- Written from deviations.json by `pnpm --filter @mod/interop-oidf run deviations`; edit the ledger, never this page. -->

The provider runs the OpenID Foundation's conformance tests on its strongest configuration and publishes, for each test that fails, why it is deliberately strict, in terms of the threat model (L1). This is the list those explanations are written from. A conformance run's expected failures name a row by its key: a failure no expected entry explains fails the run, and so do an expected entry naming no row and an expected entry no test used. A row no run uses is kept: the list is of the provider's choices, not of one plan's.

Gathering every other choice the design names is an L1 item for the gate. The rows below are the ones written so far.

Two kinds of row:
- **deviation**: the standard's normative text (MUST, MUST NOT) is not followed.
- **strict**: the standard allows it, but nextgen takes the strict side, so a test expecting the permissive side fails.

| Key | Kind | Standard | Its text | nextgen | Why | Decision |
|---|---|---|---|---|---|---|
| `par-dpop-header-only` | deviation | RFC 9449 §10.1, taken in by FAPI 2.0 §5.3.2.1 item 12 | An AS accepts the DPoP key from the PAR request's DPoP header alone | `dpop_jkt` is required in the signed JAR. A DPoP header on PAR must match it; a header alone is refused | With the header alone, a compromised Front reposts the RP's JAR with its own key's header, binds T to the attacker's key, and gets both the victim's token and the key it is bound to (Tamarin `PAR_DPOP_HEADER_ONLY`) | A44 |
| `claims-null-nested` | deviation | OIDC Core §5.5 | Members of a claims request that are not understood MUST be ignored | The direct members of `id_token` and `userinfo` written as null are read as `{}` (the same meaning). Any other null in `claims` is refused with 400 `invalid_request_object`, at PAR for a pushed request and at /login/start for one by value | The statement T the person approves is signed whole, and the signer writes no null (OIDC Core §13.3). A part of the request that cannot be signed as given is refused before the person is asked, never silently dropped from what they approve | V26 |
| `jar-dpop-jkt-required` | strict | RFC 9449 §10; FAPI 2.0 §5.3.3.1 Note 2 | `dpop_jkt` is an optional authorization request parameter; FAPI does not require the client to send it | A JAR without `dpop_jkt` is refused | When the Front relays the token request, binding the authorization to the RP's DPoP key in the signed request is what keeps a compromised Front from redeeming the code under its own key (claim 1) | L1, C2 |
| `refresh-dpop-bound` | strict | RFC 9449 §5; FAPI 2.0 §6.1 | A confidential client's refresh token need not be bound to the DPoP key; FAPI names rotating the key without losing the grant as a benefit | A confidential client's refresh family is bound to the authorization's DPoP key; a refresh under another key is refused | A family not bound to the key can be refreshed by whoever holds the token, including a compromised Front that saw it (claim 2) | L1, Q27 |
| `rar-refused` | strict | RFC 9396; FAPI 2.0 (RAR allowed) | An AS may accept `authorization_details` | `authorization_details` is refused at PAR and on every grant at the token endpoint | Per-operation authorization belongs to the RS and 4s-intent, not the IdP (V6); accepting it would make the IdP decide operations | A25 |
| `jar-required` | strict | FAPI 2.0 Security Profile; RFC 9101 | The Security Profile accepts an authorization request without a signed request object | Every authorization request is a signed JAR (PAR in a FAPI configuration, F4) | Without a signed request, a compromised Front rewrites the request the person approves (claim 1's code-grant hole). Applies only if the Security Profile plan is run | F4, 0.8 |
| `form-post-required` | strict | RFC 6749 §4.1.2; OAuth 2.0 Multiple Response Type Encoding Practices §2.1; RFC 9207; FAPI 2.0 Security Profile | An AS may return the authorization response in the redirect URI's query, made safe by `iss` (RFC 9207); the client may leave `response_mode` out | A JAR must carry `response_mode=form_post`; the response is a POST to the redirect URI, never its query | Against login CSRF: the RP's callback takes the response by `form_post` alone and checks that its `Origin` is exactly the login screen's, its `state` cookie `SameSite=None; Secure`, so a response another site sends the victim's browser is refused | R12 |
| `jar-jti-required` | strict | RFC 9101; RFC 7519 §4.1.7 | A request object may leave `jti` out | A JAR without `jti` is refused; one JAR starts one login, held by its client and `jti` until its expiry and the clock skew | The Core uses one JAR, and its `request_uri`, for one statement T alone, which needs the JAR named | A20 |
| `jar-typ-required` | strict | FAPI 2.0 Message Signing §5.3.2; RFC 9101 §10.8; RFC 8725 §3.11 | A client should send `typ` `oauth-authz-req+jwt` (FAPI 2.0 Message Signing); the AS need not require it | A JAR without `typ` `oauth-authz-req+jwt` is refused; the type is compared as a media type, without case | Explicit typing keeps a JWT made for another purpose with the same client key from being passed off as a request object | S3 |
| `par-jar-lifetime` | strict | FAPI 2.0 Message Signing §5.3.1 | An AS refuses a request object whose `exp` is more than 60 minutes after its `nbf` | PAR refuses a JAR whose `exp` is further than its own `jar-max-lifetime` (90 seconds by default) from the time it takes it; the login's start checks it again against `authorize`'s | A short `exp` and the Core's own cap keep long-lived JARs from piling up reservations | A20 |
| `state-required` | strict | RFC 6749 §4.1.1; FAPI 2.0 Security Profile §5.3.2.2 Note 4, §5.5 | `state` is recommended, not required; in FAPI 2.0, PKCE gives the protection against CSRF that `state` gave | A JAR without `state` is refused | The RP binds `state` to the browser session and redeems no response it did not begin; the login screen takes the redirect's `state` from the signed T, so a request without it leaves the RP nothing to hold the response to (login CSRF) | R3 |
| `nonce-required` | strict | OpenID Connect Core 1.0 §3.1.2.1 | `nonce` is optional in the authorization code flow | A JAR without `nonce` is refused, whether or not it asks `openid` | The ID token's `nonce` ties it to the RP's own request: one of the checks that keep a login in the browser session that asked for it | C2 |
| `request-uri-once` | strict | FAPI 2.0 Security Profile §5.3.2.2 Note 3 | An AS that uses a `request_uri` once is recommended to spend it at the point of authorization, not when the authorization page is loaded | The same JAR with the same screen keys is answered the same T; a second start with other screen keys (a reloaded screen has new ones) is refused, even before the person authenticates | The JAR's reservation binds it to one statement T and one screen's keys from its first start; a second T for the same JAR would let a compromised Front have an attacker approve it on another screen and swap that code into the victim's session (login CSRF) | A20 |
| `prompt-none-at-par` | strict | OpenID Connect Core 1.0 §3.1.2.6; RFC 9126 §2.3 | `login_required` for `prompt=none` is an authentication error response, returned to the client at its redirect URI | A pushed request asking `prompt=none` is refused at PAR with 400 `login_required`; a request by value is refused at /login/start the same way. No T is issued | Every login asks the person's passkey, so `prompt=none` is never met; PAR may answer an error itself, which tells the RP at its own server, with no round trip through the browser and no redirect the Core does not authenticate | D6 |
| `state-nonce-bound` | strict | RFC 6749 §4.1.1; OpenID Connect Core 1.0 §3.1.2.1 | `state` and `nonce` have no length limit | A `state` or `nonce` longer than 512 bytes of UTF-8 is refused with 400 `invalid_request`, at PAR and at /login/start | T, the statement the person approves, carries both and must fit its route to the screen (4096 characters); 512 each leaves room for a long client, redirect URI, scope and `claims`. The OIDF suite's 1000-character `state` is refused, which it marks a warning | V28 |
| `id-token-rs256-unsupported` | deviation | OpenID Connect Core 1.0 §15.1; OpenID Connect Discovery 1.0 §3 (`id_token_signing_alg_values_supported`) | OPs MUST support signing ID tokens with RS256, unless they return ID tokens from the token endpoint alone and let clients register only `none`; `id_token_signing_alg_values_supported` MUST include RS256 | The ID token is signed by the authority ring's one algorithm, and the metadata names that algorithm alone. nextgen's configuration signs ES256, so RS256 is neither offered nor listed. A ring under RS256 boots, warned of at every start as deprecated | FAPI 2.0 Security Profile §5.4.1 allows PS256, ES256 and EdDSA alone, and nextgen takes FAPI 2.0 with ES256 signing. Serving both would need a key per algorithm and a choice of algorithm per client (Q42) | F4 |
| `rs256-not-accepted` | strict | OpenID Connect Discovery 1.0 §3 (`token_endpoint_auth_signing_alg_values_supported`, `request_object_signing_alg_values_supported`) | Servers should support RS256 for client assertions at the token endpoint, and `none` and RS256 for request objects | Client assertions and request objects are taken under ES256, PS256 and EdDSA by default; RS256 only where the operator names it, warned of at every start. `none` is never taken, and an unsigned request is refused (`jar-required`) | FAPI 2.0 Security Profile §5.4.1 allows PS256, ES256 and EdDSA alone | F4 |
| `userinfo-not-offered` | strict | OpenID Connect Discovery 1.0 §3 (`userinfo_endpoint`); OpenID Connect Core 1.0 §5.4 | `userinfo_endpoint` is RECOMMENDED; when an access token is issued, the claims of the `profile`, `email`, `address` and `phone` scopes are returned from the UserInfo endpoint | The recommended composition offers no UserInfo endpoint (`userinfo` is opt-in), and no token introspection; the claims of the scopes asked are released in the ID token. Composing `userinfo` is a weakening choice: claims 1 and 2 are judged not to hold | A UserInfo answer is bound to neither the token it was asked with nor the request, so a compromised Front can replay an older answer of wider attributes, or answer any `sub` it likes | G1 |
| `client-keys-written-only` | strict | RFC 7591 §2 (`jwks_uri`) | A client's keys may be given by reference at its `jwks_uri`, which is preferred over the inline `jwks` for easier key rotation | A client's keys are those written in its record alone. A registry record naming a `jwks_uri` has no key, and nothing is fetched for it; a client written in the configuration may name one only as a weakening choice, which the promise judgment reports as breaking claim 2 | Keys fetched from a URL rest on whoever serves it and on the fetch's TLS, not on the publisher's signed registry, so claim 2 would depend on them | R8 |
| `webauthn-uv-required` | strict | WebAuthn Level 3 §5.5, §5.8.6, §7.2 | `userVerification` defaults to `preferred`: the Relying Party may take a response without the UV flag | Passkey ceremonies ask `userVerification: "required"`, and a response without the UV flag is refused. Any other `passkeys` `user-verification` setting breaks the promise of a new login | A new login is the person's own approval of the request with their passkey, every time (D6); user verification (fingerprint, face or PIN) makes the tap the person's, not only someone's presence | C2 |
| `webauthn-rs256-not-offered` | strict | WebAuthn Level 3 §5.4 (`pubKeyCredParams`) | Relying Parties that wish to support a wide range of authenticators SHOULD include at least -8 (EdDSA), -7 (ES256) and -257 (RS256) | Creation offers ES256 and EdDSA by default (`webauthn.algorithms`); RS256 only where the operator names it, warned of at every start. An RS256 passkey already registered is still verified | A 2048-bit RSA key holds about 112-bit security and signs by PKCS#1 v1.5, which FAPI 2.0 §5.4.1 leaves out | V22 |
| `cc-dpop-client-key` | strict | RFC 9449 §11.11 | DPoP is not client authentication: a proof is tied to the client's authentication only by sharing its TLS connection, and a cryptographic binding is left out of scope | client_credentials (opt-in, a weakening choice) takes `private_key_jwt` by a key written in the client's registry record alone, and its DPoP proof must be by that same key, the token's `cnf`; a proof by another key is refused `invalid_dpop_proof` | TLS ends at the Front, so a compromised Front could pass the client's assertion on and swap the proof for one by its own key, getting a token bound to the attacker's key in the client's name (claim 2; Tamarin `CC_PROOF_ANY_REGISTERED`) | V21 |
